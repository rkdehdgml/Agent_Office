# 3D 오픈오피스 시각화 — 설계 문서

날짜: 2026-08-10

## 목적

기존 Agent Office UI(2D 방 카드 그리드)를 하나로 이어진 3D 오픈오피스 씬으로 교체한다.
칸막이 없는 사무실 바닥에 부서별 책상이 흩어져 있고, 캐릭터가 자기 자리 근처에서
움직이다가 다른 부서 서브에이전트를 호출하면 그 책상으로 걸어가 잠깐 마주보고
돌아온다. 이벤트 로그 패널은 3D 캔버스 오른쪽에 그대로 유지한다.

기존 이벤트 서버(server/)와 상태 리듀서(officeReducer.ts)는 건드리지 않는다 — 이번
작업은 UI의 프레젠테이션 레이어(현재 Room.tsx/Character.tsx/App.css의 방 그리드)를
3D 씬으로 교체하는 것이다. 예외로, 리듀서에서 발견된 버그 하나(아래 참고)는 함께
고친다.

## 발견된 버그: `tool_name` 매핑 오류

`officeReducer.ts`의 `TOOL_STATUS`가 `Task: "업무 지시 중 📋"`로 매핑돼 있지만,
Task 2에서 실측한 실제 Claude Code 훅 로그를 보면 서브에이전트를 호출하는 도구의
실제 `tool_name`은 `"Task"`가 아니라 **`"Agent"`**다. 즉 지금 배포된 앱은 이 상태
라벨이 한 번도 정확히 뜬 적이 없다. 이번 작업에서 `TOOL_STATUS`의 키를 `Agent`로
수정한다. 이 버그 수정은 아래 "다른 부서 방문" 기능의 트리거 조건이기도 하다.

## 기술 스택

- `@react-three/fiber` (Three.js의 React 렌더러) + `@react-three/drei` (카메라 등
  헬퍼) + `three`. 기존 Vite+React+TS 스택 위에 얹는다.
- ui/ 프로젝트의 정식 devDependency로 추가한다: `three`, `@react-three/fiber`,
  `@react-three/drei`, `@types/three`.
- 검증용 헤드리스 크롬(Playwright)은 프로젝트 의존성으로 추가하지 않는다 — 구현 중
  스크린샷을 찍어 눈으로 확인하는 용도로만 임시로 사용한다 (아래 "검증 방법" 참고).

## 화면 구성

전체 레이아웃은 가로 flex: 왼쪽/중앙에 3D 캔버스(오피스 씬), 오른쪽에 고정 폭
사이드바(이벤트 로그, 기존 `EventLog.tsx` 컴포넌트를 그대로 재사용 — 내부 로직은
안 바꾸고 배치만 옮긴다).

### 카메라

고정 아이소메트릭 시점 (사용자 조작 없음). `PerspectiveCamera`를 원점을 바라보도록
비스듬히 위에서 내려다보는 각도로 고정 배치한다 (예: 위치 `[14, 16, 14]`, `lookAt`
원점, 좁은 FOV로 원근 왜곡을 최소화 — 클래식 아이소메트릭 게임 느낌). `OrbitControls`
등 카메라 조작 컴포넌트는 사용하지 않는다.

### 바닥 & 소품

- 바닥: 큰 `PlaneGeometry` 한 장 (칸막이/구역 배경색 구분 없음).
- 책상: 부서당 2~3개의 고정 슬롯 좌표를 미리 정의한 lookup(department → 슬롯 좌표
  배열)으로 관리한다. 같은 부서의 서브에이전트가 동시에 여러 개 떠도 슬롯을 순서대로
  배정한다 (슬롯보다 많으면 순환 배정 — 개인용 도구 수준의 근사치로 충분).
- 각 책상은 작은 박스(책상 본체) + 위에 얹힌 모니터 모양 박스 + 부서 색 명패로
  구성한다 (기존 2D 스프라이트의 부서 팔레트를 그대로 재사용: research-dept=파랑,
  planning-dept=보라, dev-dept=초록, 본부=주황/웜그레이).
- 소품: 화분, 정수기 등 2~4개를 고정 좌표에 배치해 사무실 느낌을 낸다. 기능에는
  영향 없는 순수 장식.

### 캐릭터

기존 2D 스프라이트의 부위 구성(머리/몸통/팔다리)을 3D 복셀(작은 Box 여러 개를
쌓은) 피규어로 옮긴다. 부서별 팔레트는 기존 값을 그대로 재사용한다. 캐릭터 렌더링은
`officeReducer.ts`의 `Character`(`status`, `active`, `agentType`, `agentId`)를
그대로 입력으로 받는다 — 상태 판단 로직은 여전히 리듀서가 소유하고, 3D 레이어는
그 상태를 "어떻게 보여줄지"만 담당한다.

## 이동/애니메이션 시스템

리듀서의 순수 상태(`OfficeState`)와는 별도로, 3D 레이어에 캐릭터별 **위치 상태**를
관리하는 훅(`useWalkers` 등)을 새로 둔다. 이 훅은 `officeReducer`가 계산한
논리적 상태(`status`, `active`)를 구독하되, 실제 좌표/이동 애니메이션은 자기가
소유한다 (기존 아키텍처의 관심사 분리 원칙 유지 — Task 4의 리비전 타이머가
`App.tsx`에 있었던 것과 같은 패턴).

각 캐릭터는 다음 중 하나의 이동 단계(phase)를 가진다:

1. **`idle`** (기본값): 자기 책상 슬롯 좌표 근처에서 미세하게 흔들리는 애니메이션
   (기존 `idle-bob`의 3D 버전). `character.active`가 `false`면 흔들림 없음
   (기존 Task 4 수정과 동일한 규칙).
2. **`walking-to-visit`**: 목표 책상 좌표를 향해 일정 속도로 보간 이동.
3. **`greeting`**: 목표 지점 도착 후 1.5초 동안 정지, 서로 마주보는 자세 (기존
   `PostToolUse` 완료 표시의 1500ms 관례와 통일). 방문받는 쪽도 이 시간 동안 잠깐
   `greeting` 단계로 전환된다 (자기 작업 애니메이션 일시 정지, 끝나면 원래 상태로
   복귀).
4. **`walking-back`**: 자기 책상 슬롯 좌표로 복귀.

### 방문 트리거

- `PreToolUse`에서 `tool_name === "Agent"`인 이벤트를 감지하면, 호출자
  (`agent_type ?? HQ_ROOM`, `agent_id ?? HQ_ROOM`)를 "대기 중인 호출자" 1개 슬롯에
  기록한다 (큐가 아닌 단일 슬롯 — 동시에 여러 호출이 겹치는 경우는 근사치로 처리,
  개인용 도구 규모에서는 충분).
- 뒤이어 `SubagentStart`가 오면, 대기 중인 호출자가 있을 경우 그 호출자 캐릭터를
  `walking-to-visit` 단계로 전환하고 목표를 새로 시작한 서브에이전트의 책상 슬롯으로
  설정한 뒤, 대기 슬롯을 비운다. 대기 중인 호출자가 없으면(예: 순서상 놓침) 아무
  애니메이션도 트리거하지 않는다 — 리듀서의 논리적 상태(방 배정, 캐릭터 등장)는
  이 매칭 성공 여부와 무관하게 항상 정확하다.
- `SubagentStop` 시 캐릭터는 기존과 동일하게 자기 책상 자리에서 비활성(회색) 처리된다
  (걸어 나가는 연출은 범위 밖 — 이번엔 추가하지 않는다).

## 이벤트 로그

기존 `EventLog.tsx`를 그대로 재사용하되, `App.tsx`의 레이아웃을 "3D 캔버스 컨테이너
+ 오른쪽 사이드바" 구조로 바꾼다. 로그 내부 로직/스타일은 변경하지 않는다 (나무
게시판 느낌으로 감싸는 정도의 컨테이너 스타일만 조정 가능).

## 제거되는 것

기존 2D 프레젠테이션 컴포넌트(`Room.tsx`, `Character.tsx`)와 `App.css`의 관련 클래스
(`.room-card`, `.room-floor`, `.sprite`, `.px` 계열 등)는 3D 씬으로 대체되므로
삭제한다 — 죽은 코드로 남겨두지 않는다.

## 테스트 & 검증

- 순수 로직은 기존 정책(officeReducer.ts에만 유닛 테스트)을 유지하되, 이번에
  새로 생기는 순수 함수들도 같은 기준으로 테스트한다: 책상 슬롯 좌표 계산 함수,
  호출자-피호출자 매칭 로직, 그리고 수정된 `TOOL_STATUS["Agent"]` 매핑.
- 3D 렌더링 자체(카메라 각도, 색상, 배치가 실제로 어떻게 보이는지)는 자동화된
  테스트로 검증하지 않는다 — 대신 **구현 과정에서 헤드리스 Chromium(Playwright)으로
  실제 스크린샷을 찍어 직접 눈으로 확인**한다. WebGL 렌더링이 이 환경에서 정상
  동작함을 이미 확인했다 (스크린샷으로 파란 사각형이 실제로 찍히는 것까지 검증).
  Playwright는 프로젝트에 정식 의존성으로 추가하지 않고, 검증 스크립트에서만
  일회성으로 사용한다.
- 최종적으로는 사용자가 직접 `npm run dev`로 열어서 움직임의 "느낌"(속도감,
  자연스러움)을 확인하는 것을 권장한다 — 정적 스크린샷만으로는 애니메이션의 실제
  체감을 완전히 검증할 수 없다.

## 범위 밖 (Out of scope)

- 카메라 조작(회전/줌/드래그)
- 캐릭터가 퇴근 시 문 밖으로 걸어나가는 연출
- 충돌 회피(캐릭터끼리 겹치는 것을 물리적으로 막는 처리) — 개인용 미니어처 느낌의
  도구에서 약간 겹치는 것은 허용
- 여러 명이 동시에 서로 다른 부서를 호출하는 경우의 완벽한 큐잉 처리 (단일 슬롯
  근사치로 충분)
